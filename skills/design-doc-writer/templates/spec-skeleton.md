# 设计规范（Spec）骨架模板

> 用法：superpowers-planner / feature-dev 写入 `doc/features/<yyyy-MM>/<feature-name>/<yyyy-MM-dd>-<sub-feature>-design.md`（`<yyyy-MM>` 为当前年月第一层目录，如 `2026-09`，`<feature-name>` 功能名目录在其下）前，必须按本骨架输出完整章节。某章节不适用时显式说明"不适用/无需"，不得省略整个骨架。
> 文档定位：Spec 面向**人审**（审阅导向）；实施计划(plan)面向 **agent 执行**，两份**独立成文、不混写**，plan 另按 `plan-skeleton.md` 输出。
> 提交约定：设计文档写入工作区后**不自动提交 git**，留待用户审阅；是否提交由用户决定。
> 语言约定：产出文档一律使用简体中文（正文、标题、注释、README、DDL 注释等）；代码标识符、命令、路径字符串保持原文。

```markdown
# <功能名称> 设计规范

> 状态：draft | active
> 当前版本：v1.x
> 最近更新：<yyyy-MM-dd>
> 关联 PRD / 参考文档：<路径>
> 文档定位：审阅导向（面向人审）；实施计划(plan)另文独立、不混写

**版本历史（变更记录规约）**：任何实质修订（含临时调整）必须**追加一行**并**递增版本号**，不得覆盖旧行；「当前版本」同步为最新行版本。主版本号用于方案/结构变更，次版本号用于局部修订与口径澄清：

| 版本 | 日期 | 变更说明 |
|------|------|---------|
| v1.1 | <yyyy-MM-dd> | <本次变更摘要> |
| v1.0 | <yyyy-MM-dd> | 初稿：<初始范围摘要> |

## 1. 结论先行摘要（一屏说清「改哪里、改成什么、影响与不动什么」）
- 改哪里：<涉及文件/模块/接口，用可检索名称，不依赖源码行号>
- 改成什么：<一句话核心结论/方案>
- 影响与不动什么：<影响面；明确不改的范围>
- 已知风险/待拍板：<如有则一句话点出，详见「风险与待拍板」>

## 2. 需求分析（为什么改）
- 原始需求 / 现状痛点：为什么现在要改
- 功能范围：怎么改的边界
- 关键讨论
- 边界与护栏（不改什么 / 不做什么）
- 禁止事项 / 禁止字段清单（如有）

## 3. 方案选择
- 考虑过的方案对比表（A/B/C）
- 选定方案及理由（理由与方案同处呈现）

## 4. 架构与设计（怎么改）
- 模块职责分配
- 调用链（改造前 vs 改造后）
- 关键设计决策
- **核心逻辑伪代码（就地贴附）**：关键流程/方法用伪代码呈现；**设计逻辑与其伪代码/SQL 就地贴在一起、理由同处呈现**，避免依赖源码行号与内部评审术语；完整实现代码由实施计划(plan)对伪代码补充完整

## 5. 接口定义与 API 设计
- **内部接口定义**：本次涉及的核心接口及内部方法签名（Service/Strategy/Mapper 等）
- **对外 API**：路径、方法、签名（无对外 API 则显式说明）
- 请求/响应 DTO
- 枚举与常量

## 6. 数据模型
- 表结构 / 字段说明
- **字段映射**：如为 Excel/文件导入需求，须提供「Excel 列 → 表字段」映射表（Excel 列、表字段、转换方式，标注同名/类型转换/语义改名/丢弃）
- **DDL**：涉及建表、加列、改表时，DDL 脚本输出到 `doc/features/<yyyy-MM>/<feature-name>/sql/` 并在本文内联，就近说明设计理由；如无需 DDL 则显式说明"无需 DDL"
- **DML**：涉及初始化数据、字典、码值映射时，附 DML SQL；如无需 DML 则显式说明"无需 DML"

## 7. 非功能需求
- 幂等 / 并发 / 性能 / 数据一致性 / 安全（按需覆盖）

## 8. 错误处理
- 异常场景 → 错误码 → 用户提示

## 9. 影响面与回滚
- 影响的既有模块/表/任务
- 兼容性与回滚方案

## 10. 风险与待拍板（单列放明面）
- 需知悉/待拍板的风险、口径、假设逐条列出，注明待谁拍板/确认

## 11. 测试策略
- 单元测试范围
- 集成测试场景
- 验证命令（编译/测试命令，对接 feature-dev）

## 12. 验收标准
- [ ] 可验证的完成条件

---

## 与实施计划(plan)的分工
- 本文面向人审，供评审拍板；实施计划(plan)另文面向 agent 执行
- 本文给出设计逻辑与伪代码/SQL 及其理由；完整可编译实现代码、TDD 步骤、逐文件验证命令与验收由 plan 输出
- 两份独立成文、不混写：plan 执行时以 plan 为主入口、本文仅作背景资料
```
